## Measured host costs and scope

The final performance reviewer used pinned Node 24.22.2 on this Apple arm64 host, synthetic worlds in a temporary file repository, one warmup and five measured calls per operation. File save began with an **already encoded** world snapshot, so its figure excludes codec encode and coordinator slice/legacy preparation. File load also excludes coordinator publication. These are component medians, not a sum or full save/load latency.

| Entities | File size | Codec encode | File save | File load |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 2,320 bytes | 0.33 ms | 0.92 ms | 0.52 ms |
| 100 | 105,552 bytes | 8.19 ms | 10.67 ms | 10.23 ms |
| 500 | 523,952 bytes | 40.58 ms | 50.59 ms | 50.02 ms |

An isolated one-slot, 523,948-byte `listSlots()` run after three warmups took **50.53 ms median** over 20 calls (48.94–54.97 ms range). Task 3.2's smaller explicit-list benchmark wrote **100 slots totaling 232,500 bytes** and took **23.1–26.7 ms**, **24.9 ms median** over ten warmed runs. These different populations do not establish a universal per-slot bound. The shipped browser frame loop does not call save, load or list; future player autosave integration must measure representative maximum worlds and slices on the actual 2019 Intel target before claiming a presentation budget. The latest commit hook's test check took **23,822 ms** on this host; its reference-Mac under-five-second target remains unverified.
